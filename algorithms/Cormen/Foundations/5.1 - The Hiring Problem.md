# 5.1 The Hiring Problem

## The scenario

You need to hire a new office assistant. An employment agency sends one candidate each day. Interviewing the candidate costs a small fee. **Hiring** is much more costly because the current assistant must be fired and a substantial hiring fee paid. You always want the best person on the job, so after each interview, if the candidate is better qualified than the current assistant, you fire the current one and hire the new candidate. You are willing to pay the resulting price but want to estimate what that price will be.

## The HIRE-ASSISTANT procedure

```
HIRE-ASSISTANT(n)
1  best = 0    // candidate 0 is a least-qualified dummy candidate
2  for i = 1 to n
3      interview candidate i
4      if candidate i is better than candidate best
5          best = i
6          hire candidate i
```

## Cost model

We focus not on running time but on **costs incurred by interviewing and hiring**. Interviewing has low cost cᵢ; hiring has high cost cₕ. Letting m be the number of people hired, the total cost is O(cᵢn + cₕm). Since we always interview n candidates, we focus on analyzing **cₕm** — the hiring cost — which varies with each run.

This scenario serves as a model for a common computational paradigm: finding the maximum (or minimum) in a sequence by examining each element and maintaining a current "winner."

## Worst-case analysis

The worst case occurs when candidates come in strictly increasing order of quality — every interview triggers a hire — yielding cost **O(cₕn)**.

We have no control over the order in which candidates arrive. What we *can* do is ask what we expect in a typical or average case.

## Probabilistic analysis

**Probabilistic analysis** is the use of probability in the analysis of problems. Most commonly, it analyzes the running time (or some other quantity) of an algorithm. To do it, we must know — or make assumptions about — the **distribution of inputs**. Then we compute the **average-case running time**: average over the distribution of possible inputs.

We must be careful when deciding on the input distribution. For some problems, a reasonable assumption is possible; for others, no reasonable description exists.

For the hiring problem, we assume that applicants arrive in **random order**. There is a total order on candidates, so each can be ranked uniquely from 1 to n (higher rank = better qualified). The ordered list of ranks ⟨rank(1), rank(2), …, rank(n)⟩ is equally likely to be any of the n! permutations — a **uniform random permutation**.

## Randomized algorithms

To use probabilistic analysis, we need to know something about the distribution of inputs — often we don't. We may still use **probability and randomness** as a tool for algorithm design and analysis, by making the algorithm random itself.

For the hiring problem, the candidates may appear to come in random order — but we have no way of knowing whether they really are. To develop a **randomized algorithm**, we must control the order in which we interview candidates. Change the model slightly: the agency sends us a list of n candidates in advance, and each day **we** choose, randomly, which candidate to interview. Even knowing nothing about the candidates (besides their names), we have gained control of the process and enforced a random order.

More generally, an algorithm is **randomized** if its behavior is determined not only by its input but also by values produced by a **random-number generator** RANDOM. A call RANDOM(a, b) returns a uniformly chosen integer between a and b inclusive. In practice, a **pseudorandom-number generator** is used.

When analyzing the running time of a randomized algorithm, we take the **expectation** of the running time over the distribution of values returned by the random-number generator. We call this the **expected running time**. In general:

- The **average-case** running time is used when the probability distribution is over the inputs.
- The **expected running time** is used when the algorithm itself makes random choices.
