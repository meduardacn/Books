# 5.3 Randomized Algorithms

In Section 5.2 we showed how knowing a distribution on the inputs helps analyze average-case behavior. Often we have no such knowledge. If we cannot assume any distribution, we may be able to use a **randomized algorithm**.

For the hiring problem, instead of *assuming* a distribution of inputs, we *impose* one: before running the algorithm, **randomly permute the candidates** to enforce that every permutation is equally likely. We still expect to hire approximately ln n times — but now this is true for **any** input.

## Probabilistic vs. randomized

- Probabilistic analysis assumes randomness in the input; the algorithm is deterministic.
- Randomized algorithms inject randomness into the algorithm; the input can be anything.

With randomization, **no particular input elicits worst-case behavior**. Even your worst enemy cannot produce a bad input. The algorithm performs badly only if the random-number generator produces an unlucky permutation.

## RANDOMIZED-HIRE-ASSISTANT

```
RANDOMIZED-HIRE-ASSISTANT(n)
1  randomly permute the list of candidates
2  best = 0    // candidate 0 is a least-qualified dummy candidate
3  for i = 1 to n
4      interview candidate i
5      if candidate i is better than candidate best
6          best = i
7          hire candidate i
```

## Lemma 5.3

The expected hiring cost of RANDOMIZED-HIRE-ASSISTANT is O(cₕ ln n).

**Proof.** After permuting the input, we have a situation identical to the probabilistic analysis of HIRE-ASSISTANT.

The difference between Lemmas 5.2 and 5.3: Lemma 5.2 assumes the input is random; Lemma 5.3 makes no such assumption but pays the cost of randomly permuting.

## Randomly permuting arrays

We discuss two methods for randomly permuting an n-element array A (assumed to contain elements 1 through n).

### PERMUTE-BY-SORTING

Assign each element a random priority and then sort:

```
PERMUTE-BY-SORTING(A)
1  n = A.length
2  let P[1..n] be a new array
3  for i = 1 to n
4      P[i] = RANDOM(1, n³)
5  sort A, using P as sort keys
```

Priorities in the range 1 to n³ are chosen so all entries are likely to be unique (probability ≥ 1 − 1/n). The time-consuming step is sorting — Ω(n lg n) for comparison sorts. Achieving this bound is possible (merge sort).

### Lemma 5.4

Procedure PERMUTE-BY-SORTING produces a **uniform random permutation** of the input, assuming all priorities are distinct.

**Proof.** Consider the permutation in which each A[i] receives the i-th smallest priority. This occurs with probability exactly 1/n!. By induction and conditional probability, each of the n! possible permutations is equally likely.

### RANDOMIZE-IN-PLACE

A better method runs in O(n) time. It chooses A[i] randomly from among elements A[i..n], then never alters A[i]:

```
RANDOMIZE-IN-PLACE(A)
1  n = A.length
2  for i = 1 to n
3      swap A[i] with A[RANDOM(i, n)]
```

### Lemma 5.5

Procedure RANDOMIZE-IN-PLACE computes a **uniform random permutation**.

**Proof using a loop invariant:**

> Just prior to the i-th iteration of the for loop of lines 2–3, for each possible (i−1)-permutation of the n elements, the subarray A[1..i−1] contains this (i−1)-permutation with probability (n−i+1)!/n!.

- **Initialization:** Before the first iteration, A[1..0] is empty, which contains the unique 0-permutation with probability 1 = n!/n!.
- **Maintenance:** Each iteration extends a known (i−1)-permutation by one randomly chosen element. The probability calculation works out to (n−i)!/n!.
- **Termination:** At i = n+1, A[1..n] is a given n-permutation with probability 1/n!.

Thus RANDOMIZE-IN-PLACE produces a uniform random permutation.

A randomized algorithm is often the simplest and most efficient way to solve a problem; the book uses them occasionally throughout.
